# FIXTURE-SOURCES.md — Web sources for Access test objects

> Research assignment (2026-11-01): find Access database files (`.mdb`/`.accdb`)
> on the web that serve as test objects. Complements docs/TESTING.md §4
> (golden files) and decision default #2 (oracle fixtures = pinned jackcess
> test files). Every recommended binary was downloaded, magic-byte checked
> (`Standard Jet DB` / `Standard ACE DB` at offset 0x04) and hashed on
> 2026-11-01. Language English (binding), see docs/PLAYBOOK.md §2.

## 1. Selection criteria

1. **Clean-room compatibility** — test data only, no Microsoft code, no
   decompiled artifacts. Files *generated by* open-source libraries
   (jackcess, MDB Tools tooling) or *created with real Access* are both fine;
   what matters is provenance we can pin (repo + commit + per-file sha256).
2. **Format coverage** — Jet3 (Access 97, deferred per item L1), Jet4
   (Access 2000/2003, `.mdb`), ACE (Access 2007/2010/2019, `.accdb`).
3. **Feature coverage** — the matrix our parser must survive: overflow rows,
   deleted rows/columns, index variants, unicode/compression, OLE/memo
   (LVAL chains), passwords/encryption, unusual dates, complex types.
4. **Immutability** — a fixture is evidence. Never open it in an application
   that can write (see §4 case study); pin and verify hashes.

### D. Marginal / not recommended

- `clamav-fuzz-corpus` (`database/MDB/sample.mdb`): single generic seed, no
  provenance story beyond the repo.
- File-sample websites (`file-examples.com` etc.): weak provenance, no pin.
- Open-data portals (government `.mdb` datasets): ad-hoc provenance; useful
  later for scale testing, not for pinning now.
- **Evil inputs** (truncated, flipped magic, hostile names): synthesize
  locally as mutations of the pinned files — docs/TESTING.md §5, LESSONS A1.
  A downloaded "corrupted file" can never be reproduced to its origin bytes.

**Creation recipe** (scripted builder, proven end to end; prerequisites:
Windows x64 with the Access build above (Microsoft 365,
`16.0.20527.20112`); the installed build keeps `AccessVBOM` unset, so
every object-text import goes through `SaveAsText`/`LoadFromText` — no
Trust Center change):

1. Scratch directory outside the repository; `Access.Application` COM
   automation with `AutomationSecurity` forced to disable macros (the
   fixture defines no `AutoExec` anyway); fail-fast per step — a failing
   COM call aborts the build (a poisoned session cascades).
2. `NewCurrentDatabase "<scratch>/programmability.accdb"`.
3. Tables through `CurrentDb.Execute` DDL (`CREATE TABLE` with `COUNTER`
   primary keys and `FOREIGN KEY` constraints); rows through `INSERT`
   statements — deterministic, self-authored content.
4. Multi-value field `Tags`: `CreateField("Tags", 109)` (`dbComplexText`)
   plus DAO property append (`DisplayControl`, `RowSourceType`,
   `RowSource`, `BoundColumn`, `ColumnCount`, `ColumnWidths`,
   `AllowMultipleValues`); a plain text field with only the properties
   does NOT become complex. Values are written through the parent
   recordset in edit mode and the child recordset of the complex field
   (`rs.Edit` → `rs.Fields("Tags").Value.AddNew/Update` → `rs.Update`);
   SQL `UPDATE`/`INSERT` refuse multi-value columns.
5. Queries through `db.CreateQueryDef` with the SQL above.
6. Macros through `LoadFromText` (`acMacro`): header
   `Version =196611` / `PublishOption =1` / `ColumnsShown =0`, then one
   sibling `Begin`/`End` block per action with `Action ="…"`, `Argument
   ="…"` lines (multiple actions in one block are a parse error).
7. Forms and reports through `LoadFromText` (`acForm`/`acReport`):
   header `Version =20` / `VersionRequired =20`, `Begin Form` (or
   `Begin Report`) properties, a plain `Begin` container with a
   `Begin Section` (Detail) holding the controls (attached labels nest
   inside their control's `Begin`); the module source follows after
   `CodeBehindForm`. Forms without code omit the `CodeBehindForm`
   section. Never use `CreateForm` — its unsaved-design save paths pop
   dialogs; `SaveAsText` requires saved objects.
8. Modules and classes through `LoadFromText` (`acModule`) with the
   object text encoded **cp1252/ANSI** (UTF-16LE input is decoded as
   ANSI and corrupts the source). Class module texts carry
   `VB_GlobalNameSpace`/`VB_Creatable`/`VB_PredeclaredId`/`VB_Exposed`
   attribute lines and no `VB_Name`; the import order is the module
   storage order.
9. `CloseCurrentDatabase`, then `CompactRepair` through a short-lived
   second instance, `Quit acQuitSaveNone` (never `acQuitSaveAll` — it
   saves unsaved designs and pops the Save As dialog) — no
   `MSACCESS.EXE` process or `.laccdb` lock file left behind.
10. Verify with the datacraft decoder before committing: VBA extraction
    (module list, order, source incl. umlauts), macro inventory,
    `native_queries()` answers the precise attribute-12 `Unsupported`,
    SQL materialization reads every table's rows, the four
    programmability suites decode the file.
11. Pin: sha256 into `fixtures/manifest` with provenance "created with
    Microsoft Access 16.0.20527.20112 on <date> by DataCraft
    contributors". The finished file is never reopened in Access after
    it is committed; regeneration reruns the builder in a scratch
    directory (`tools/fixture-build/build.ps1`, object texts under
    `tools/fixture-build/objects/`, SQL text under
    `tools/fixture-build/sql/`). The object texts live in the
    repository, not inside the committed fixture — reading them out of
    the fixture would mean opening it in Access, which fixtures never
    survive (§4). The inventory comparison runs through the datacraft
    decoder snapshot; the rebuilt file's hash is recorded but
    intentionally differs from the pin (creation timestamps are inside
    the file).

Empirical values (macro argument strings, module storage order, the exact
attribute set) are read off the built file and pinned in the ported suites —
the recipe fixes the object set, not the binary layout.

The three ACE fixtures are pinned as `fixtures/testV2007.accdb`,
`fixtures/testV2010.accdb` and `fixtures/attachmentsV2016.accdb` (hashes and
`repo@commit` provenance in `fixtures/manifest`; the CI fixtures job verifies

## 4. Provenance case study: `fixtures/testV2000.mdb` was rewritten by Access

Finding (2026-11-01): the on-disk fixture does **not** match the pin —
it is not the jackcess file committed at `be0a2139`. The cause is not a bad
download: the file was **once opened in real Microsoft Access**, which rewrote
parts of it on open (no explicit save). Evidence:

| Metric | Value |
|---|---|
| common-prefix bytes identical | 3 034 534 / 3 043 328 = 99.71 % |
| aligned pages differing | 23 of 743 (header page, TDEF pages 2/3/5, index leaf + data pages of the system-table area) |
| pages appended | +22 (16 data — several with `LVAL` owner, 4 TDEF, 5 index leaf) — new/extended system tables incl. memo data |
| header page 0x000–0x0FF | byte-identical (product/version/creation region unchanged) |
| header page beyond 0x100 | exactly 1 byte changed (0x0E02 `31→A5`) |

Consequences:

1. **sha mismatch explained** — recorded pin hash (`126bad49…`) matches the
   pristine jackcess file; the on-disk file (`5caab9ba…`) is an
   Access-touched descendant. Both are valid Jet4 databases; the user-table
   pages are untouched.
2. **T2 material, not garbage** — the touched variant shows how *real
   Access* (the ground-truth writer for the bit-for-bit goal) packs the same
   system catalog. Our oracle harness behaves measurably differently on the
   two variants (pristine: 22 MSysObjects rows decode; touched: different
   parse path). Compare both when resolving the tail semantics.
3. **Process rule (LESSONS A1/adjacent)** — fixtures are immutable evidence:
   never open them in Access or any Jet/ACE writer; work on copies; verify
   pinned sha256 in CI. Tracked in BACKLOG as T3.

## 6. Pinning procedure

1. Commit fixtures under `fixtures/` (`.gitattributes` already marks
   `*.mdb`/`*.accdb` binary); reference source as `repo@commit`.
2. Replace the single `jackcess-pin.txt` with a `fixtures/manifest` listing
   every fixture with `source repo@commit` + sha256.
3. CI job re-verifies committed hashes (cheap, offline) — a drifted or
   hand-edited fixture fails the build instead of poisoning the oracle.
4. Rule: fixtures are never opened in writer-capable applications; any
   manual byte experiment runs on a copy.
